# Prepared-runtime Canary verification

The managed KVM validator can select a prepared Agent Zero disk or the shared Claude Code/Codex dependencies on a compatible sealed provisioner. These are operator-only Canary controls. Ordinary launches stay on the stock disk; the image does not preconfigure a tenant or change the normal CLI updater.

1. Qualify the exact disk bytes offline. Follow the [Bux dependencies](../../dashboard/scripts/bake-bux-dependencies.md) or [Agent Zero](../../dashboard/scripts/bake-agent-zero.md) gate. Require a standalone image, two clean BIOS boots through QGA with distinct identities, and no retained tenant state. The Agent Zero check must run the pinned image without pulling it. Staging never substitutes for these checks.
2. Take matched stock measurements before applying the scope. Use the standing QA owner and one tagged fixture at a time. Record the browser setting, reserved and maximum CPU and memory, serving Git revision, host provisioner seal, and Open and first-reply times. Delete the fixture and verify its row and host resources are gone before another launch.
3. Stage the verified digest on the nominated Canary host. On a serving Git revision with runtime pilot settings, use the Canary database operator to insert a `bux-dependencies` or `agent-zero` row in `public.hivra_canary_launch_pilots` with the nominated `host_id`, exact `image_sha256` and standing QA `owner_id`. Read it back and confirm the serving revision and compatible host bundle before submitting a fresh browser-off launch. Changing a row on a compatible build needs no new deployment; older revisions may still read retired deployment variables.
4. Prove the owned operation used the intended digest before interpreting timing. Repeat the stock resources and prompt, verify an authenticated Files write/read where supported, and retain the first-reply recording separately from the timing receipt. One observation is not a fleet percentile or proof that the image caused every timing change.
5. Delete the exact tagged fixtures and verify both database and host cleanup. Delete only your exact pilot row, verify its absence and drain launches already in flight with the old row before removing the staged disk. For an older deployment that captured a pilot in environment variables, remove only its scoped settings and wait for a later Git deployment without those settings before removing the disk.
