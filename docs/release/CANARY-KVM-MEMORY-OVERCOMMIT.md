# Canary KVM memory overcommit

This is an off-by-default operator pilot, not a customer capacity promise. It has no production setting or automatic activation. The database migration creates no setting row.

## What runs where

The dashboard reads the grant per request on canonical Git Canary only. It is scoped to the exact pve11 registry entry, one configured pilot owner, paid managed KVM launches and disk wakes for Hermes and Claude Code, and the Canary provisioner channel. It never applies to VM 9302, standby claims, portable moves, self-managed targets, napping VMs, or the Classic lane. Existing placement selection, database reservations, CPU/disk checks and wake-slot gates keep their independent authority; a host grant is not a placement override. No guest memory size, balloon floor, or other entitlement is changed.

`hivra-host-capacity-admission` executes on the Proxmox host under the common allocation lock. A qualifying launch uses the exact Canary bundle seal, writes the existing durable selected intent and holds the lock through visible VM start. A disk wake checks the exact helper digest and reserves a separate `wake-<vmid>.selected` intent before sending `qm start`. It clears the wake intent under the lock only after fresh binding, running state and PID evidence agree. An ambiguous return leaves the marker in place and blocks further admissions through the updated helper until an operator proves the same VM is counted or that its start did not happen.

Positively stopped VMs do not consume active RAM; the waking VM is charged its full configured maximum before start. Naps, unmatched or newly active guests, and pending allocations are not credited as reclaimable. Only exact operator-enrolled running guests can earn measured PSS credit, and every active configured maximum still counts toward the hard entitlement ceiling. Direct `qm start`, platform autostart and any writer using a different lock are outside this admission contract. Before any authorized density run, identify those writers on the target and exclude competing allocations from the pilot window.

## Stock-template density fixtures

Two 4 GiB guests alone cannot offset an 8 GiB reserve: even if both registered zero PSS, their combined credit is at most the reserve, so measured usage plus reserve cannot stay within physical RAM once configured active entitlement exceeds it. A density run can use additionally measured operator clones from pve11 template 9007; fixtures outside the exact enrollment still cost their full maximum.

For a separately authorized run, add exact `VMID:hivra-qa-mem-<32 hex>` identities to the existing owner's `measured_qa_clones` list. The grant excludes retained Native or Classic tenant allocations. Request a fresh, unused VMID in 9300–9399 except 9302 with the authenticated Canary operator action `POST /api/ops/hivra/canary-memory-qa-clone`: explicit `apply: true`, the scoped `ownerId`, exact numeric `vmid`, exact `tag`, and reviewed `templateConfigSha256` of the current stock template configuration with its terminal newline. The caller cannot pick a host or pass a ratio or telemetry. The action refuses a missing, stale, or mismatched grant or bundle.

The pve11 wrapper rejects already claimed or occupied VMIDs and templates with autostart enabled. It links only from that exact stock template, removes networking, and uses the normal host helper and durable start fence under the allocation lock. Each 4 GiB fixture has a 0.25-vCPU ceiling. The action derives the aggregate CPU ceiling from pve11's active placement row and ordinary CPU ratio, capped at the host helper's 4× limit. It also checks actual storage headroom; RAM mode never overrides CPU or storage refusal.

The wrapper records the clone's host boot ID, exact QEMU PID and process start time after guest-agent health is confirmed. Clones are still fully charged at startup, for at least the first 120 seconds, and if any exact enrollment or process proof becomes absent or stale. The operator must not send raw `qm start` for these fixtures. Claim before use and reserve cleanup time; after exact identity and pending work are reconciled, remove only those owned fixtures and their matching enrollment and VMID references. A failed or indeterminate request is not permission to remove a claim or retry around the fence.

## Release and stop

Git Canary and the pve11 installed bundle are separate targets. After an authorized Canary merge, verify the Git-sourced deployment SHA and the additive DB migration. Separately install or converge the exact sealed `2026.11.28.2` bundle at `/root/hivra-provisioner-canary` on pve11 through the supported, identity-checked provisioner bundle operation. Verify the installed version and full manifest digest before issuing a grant. Keep the default channel and other hosts unchanged. A matching Vercel revision alone does not establish runtime adoption.

Only after those gates pass, an authorized operator can set the exact owner, ratio, expiry and individually measured identities in `hivra_canary_memory_overcommit`. At the same affirmative customer-health check, pin the host boot ID, swap-in/out and OOM counters, and currently used swap in KiB. The fresh baseline can attest up to 64 KiB of existing swap; further swap use, any counter change (including reset), guest QEMU swap, memory pressure or a reboot refuses the pilot. Never clear telemetry, turn off swap, or rebaseline through an unresolved health change to obtain an admit.

The inherited customer-health stop rule requires an affirmative check no older than ten minutes; if it goes bad or cannot be established, set `customer_health_ok = false` or disable the setting rather than refreshing it. New requests immediately lose the grant, and already-read grants expire within 90 seconds or sooner at the health or setting deadline. This revokes future relaxed admission; it does not shrink, stop, move, or delete running VMs. Do not assume in-flight work has stopped until reconciled. Do not revert the host helper to an older version while a wake intent is unresolved: older versions cannot see that fence.

Acceptance must still verify real launch and saved-memory or cold-disk wake against that exact Git revision and installed seal, including simultaneous wakes that cannot fit, denials when health or telemetry is missing or unsafe, full charge for unrelated VMs, and unchanged pre-existing guests. Record measured PSS and host headroom, swap, OOM and memory PSI; no live qualification is implied by the offline tests.
