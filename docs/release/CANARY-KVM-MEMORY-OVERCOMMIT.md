# Canary KVM memory overcommit

This is an off-by-default operator pilot, not a customer capacity promise. It has no production setting or automatic activation. The database migration creates no setting row.

## What runs where

The dashboard reads the singleton database grant per request on canonical Git Canary only. No deployment setting is needed. The grant is scoped to one exact active registry entry and one pilot owner, paid managed KVM launches and disk wakes for Hermes and Claude Code, and the Canary provisioner channel. For managed launch and wake, the selected or persisted placement must match the grant's host. The registry identity must also match the actual host's kernel hostname; no matching row means no pilot. It never applies to VM 9302, standby claims, portable moves, self-managed targets, napping VMs, or the Classic lane. Existing placement selection, database reservations, CPU/disk checks and wake-slot gates keep their independent authority; a host grant is not a placement override. No guest memory size, balloon floor, or other entitlement is changed.

`hivra-host-capacity-admission` executes on the Proxmox host under the common allocation lock. A qualifying launch uses the exact Canary bundle seal, writes the existing durable selected intent and holds the lock through visible VM start. A disk wake checks the exact helper digest and reserves a separate `wake-<vmid>.selected` intent before sending `qm start`. It clears the wake intent under the lock only after fresh binding, running state and PID evidence agree. An ambiguous return leaves the marker in place and blocks further admissions through the updated helper until an operator proves the same VM is counted or that its start did not happen.

Positively stopped VMs do not consume active RAM; the waking VM is charged its full configured maximum before start. Naps, unmatched or newly active guests, and pending allocations are not credited as reclaimable. Only exact operator-enrolled running guests can earn measured PSS credit, and every active configured maximum still counts toward the hard entitlement ceiling. Direct `qm start`, platform autostart and any writer using a different lock are outside this admission contract. Before any authorized density run, identify those writers on the target and exclude competing allocations from the pilot window.

## Stock-template density fixtures

Two 4 GiB guests alone cannot offset an 8 GiB reserve: even if both registered zero PSS, their combined credit is at most the reserve, so measured usage plus reserve cannot stay within physical RAM once configured active entitlement exceeds it. A density run can use additionally measured operator clones from the exact stock template named by the grant's optional `qa_template_vmid`. If no template is set, the clone action is off. Fixtures outside the exact enrollment still cost their full maximum.

For a separately authorized run, add exact `VMID:hivra-qa-mem-<32 hex>` identities to the existing owner's `measured_qa_clones` list. The grant excludes retained Native or Classic tenant allocations. Request a fresh, unused VMID in 9300–9399 except 9302 with the authenticated Canary operator endpoint `POST /api/ops/hivra/canary-memory-qa-clone`: `action: "start"` (the default), explicit `apply: true`, the scoped `ownerId`, exact numeric `vmid`, exact `tag`, and reviewed `templateConfigSha256` of the current stock template configuration with its terminal newline. The caller cannot pick a host or pass a ratio or telemetry. The endpoint refuses a missing, stale, or mismatched grant or bundle.

The host wrapper rejects already claimed or occupied VMIDs and templates with autostart enabled. It links only from that exact stock template, removes networking, and uses the normal host helper and durable start fence under the allocation lock. Each 4 GiB fixture has a 0.25-vCPU ceiling. The action derives the aggregate CPU ceiling from the configured host's active placement row and ordinary CPU ratio, capped at the host helper's 4× limit. It also checks actual storage headroom; RAM mode never overrides CPU or storage refusal.

Start returns `running_full_charge` only when the running QMP peer is the exact live QEMU process and its bound configuration is confirmed. The wrapper records the clone's owner, template, host boot ID, QEMU PID and process start time in `qa-memory-<vmid>.started` before clearing the fence. It does not wait for the guest agent or grant any PSS credit. An ambiguous start still leaves the start fence in place.

Once the guest agent is ready, send `action: "qualify"` to the same endpoint with `apply: true` and the same owner, numeric VMID and tag, omitting the template digest. Qualification checks a fresh grant, checks the exact start identity and isolated configuration before and after a fresh guest-agent ping, and only then writes `qa-memory-<vmid>.enrolled` and returns `qualified`. A guest not yet ready stays at full charge without a startup fence; recheck it before requesting qualification again. Qualification does not start or restart a VM, accept a fixture started through the old wrapper without a matching start receipt, or reconcile an ambiguous start. The admission helper also requires at least 120 seconds of process age and independently verifies the enrollment and running process before awarding PSS credit.

Do not send raw `qm start` for these fixtures. Claim before use and reserve cleanup time; once identity and pending work are reconciled, remove only the owned fixtures and their matching start receipts, enrollments and VMID references. A failed or indeterminate request is not permission to remove a claim or retry around the fence.

## Release and stop

Git Canary and the installed host bundle are separate targets. After an authorized Canary merge, verify the Git-sourced deployment SHA and the additive DB migration. The two-step clone endpoint requires exact sealed `2026.11.28.3` at `/root/hivra-provisioner-canary`; the existing paid launch and disk-wake pilot can still use the sealed predecessor. Separately install or converge the new version on the configured host through the supported, identity-checked provisioner bundle operation. Verify the installed version and full manifest digest before using it. Keep the default channel and other hosts unchanged. A matching Vercel revision alone does not establish runtime adoption.

Only after those gates pass, an authorized operator can set the exact host, owner, optional QA template, ratio, expiry and individually measured identities in the singleton `hivra_canary_memory_overcommit` setting. The configurable hard ratio cannot exceed 2.0×; it is an upper bound, not a measured or approved density. Increase in stages only while all live checks hold, and stop below the target if any gate refuses. At the same affirmative customer-health check, pin the host boot ID, swap-in/out and OOM counters, and currently used swap in KiB. The fresh baseline can attest up to 64 KiB of existing swap; further swap use, any counter change (including reset), guest QEMU swap, memory pressure or a reboot refuses the pilot. Never clear telemetry, turn off swap, or rebaseline through an unresolved health change to obtain an admit.

The inherited customer-health stop rule requires an affirmative check no older than ten minutes; if it goes bad or cannot be established, set `customer_health_ok = false` or disable the setting rather than refreshing it. New requests immediately lose the grant, and already-read grants expire within 90 seconds or sooner at the health or setting deadline. This revokes future relaxed admission; it does not shrink, stop, move, or delete running VMs. Do not assume in-flight work has stopped until reconciled. Do not revert the host helper to an older version while a wake intent is unresolved: older versions cannot see that fence.

Acceptance must still verify real launch and saved-memory or cold-disk wake against that exact Git revision and installed seal, including simultaneous wakes that cannot fit, denials when health or telemetry is missing or unsafe, full charge for unrelated VMs, and unchanged pre-existing guests. Record measured PSS and host headroom, swap, OOM and memory PSI; no live qualification is implied by the offline tests.
