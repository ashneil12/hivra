# Moving an existing Hermes agent onto the official Hermes

Status: design, being built on Canary. Nothing here has touched production.

## What the owner sees

On an old Hermes agent's page (a `hermes_instances` row), when the official Hermes lane is on
(`isHermesComputerEnabled()`), one card replaces the old update cards:

> **Move to the official Hermes.** Your agent moves to a new computer running the official Hermes,
> which you update yourself. Your chats, memory, skills, settings, scheduled tasks, chat channels and
> files come with it. It takes about ten minutes and your agent is offline meanwhile. Your current
> computer is kept for 7 days, so you can undo the move.

Progress shows real steps only: setting up the new computer, packing your data, copying it, unpacking
and checking it, done. It ends in one of three states:

- **Moved.** The old page sends the owner to the new agent. The new agent shows "Moved from <name> on
  <date>. The old computer is kept until <date>." with **Undo move**.
- **Not moved, nothing lost.** Something did not check out. The old agent was started again as it was,
  and the new computer was removed. The card says what failed.
- **Needs attention.** The old agent could not be started again. An operator is alerted.

## Why a new computer

Old agents run Hermes in Docker on a Hivra image (fork or overlay) that Hivra updates. The official lane
runs Hermes installed by Hermes's own installer and updated with `hermes update`. Converting a VM in
place would leave Docker, Caddy and the old sidecars behind and could not be undone cleanly. A fresh
official computer plus Hermes's own `hermes import` is the documented upstream way to move Hermes to a
new machine, and the old VM stays as the undo for 7 days.

## The data

Everything the user owns on an old box:

| What | Where on the old box | How it moves |
|---|---|---|
| Hermes home (chats `state.db`, memory, skills, cron jobs, profiles, `config.yaml`, `.env` with provider keys and channel tokens, `auth.json`, SOUL.md) | docker volume `agent-<id>_webui-state` (`/var/lib/docker/volumes/agent-<id>_webui-state/_data`) | zipped with upstream `hermes backup` exclusions, restored with the official `hermes import --force` |
| Workspace files | docker volume `agent-<id>_webui-workspace` | tar.zst, extracted to `/home/bux/workspace`, with `/workspace` a symlink to it so paths in memory and cron jobs still work |
| Bankr wallet | DB `instance_bankr_wallets` (instance_id) plus `BANKR_*` in `.env` and `bankr:` in `config.yaml` | env and config move with the Hermes home; the DB row is relinked (`instance_id = null`, `hivra_agent_id = <new>`) |
| Composio and Hivra tools | `mcp_servers.composio` / `mcp_servers.hivra_*` in `config.yaml` | move with `config.yaml` (plain upstream MCP servers) |

Not moved: the Hivra browser sidecar profile (Hermes computers install Hermes with `--skip-browser`),
the Hivra web UI, the sidecar and the old Caddy setup.

## How the bytes travel

Old and new computers can sit on different Proxmox hosts, and hosts must not be opened to each other.
So the bytes go guest to Supabase Storage to guest, and the dashboard only mints short-lived signed
URLs:

1. The old guest packs the data, encrypts it with a per-move key (`openssl enc -aes-256-cbc -pbkdf2`),
   splits it into parts of at most 45 MB (the project upload limit is 50 MB), and records each part's
   size and sha256.
2. The dashboard mints one signed upload URL per part in the private bucket `hermes-moves`
   (`<moveId>/<part>`). The old guest uploads with `curl -T`.
3. The dashboard mints signed download URLs. The new guest downloads, checks every part's sha256
   against the values stored in the move row, joins, decrypts and imports.
4. After a successful import the parts are deleted from storage.

The per-move key is generated by the dashboard, stored only as `encryptSecret(...)` in the move row,
and travels to the guests inside the job script body (never a process argument, never logged).

## The jobs

Each guest job runs as a detached `systemd-run` unit on the guest, so a dashboard request never waits
on it, and writes `/var/lib/hivra-move/<moveId>/status.json`:

```json
{ "state": "running|done|failed", "step": "<job step>", "message": "<plain English>",
  "updatedAt": "<iso>", "result": { } }
```

| Job | Runs on | Reached with | Does |
|---|---|---|---|
| `pack` | old guest, root | `sshExec(hostIp, cmd, { proxmoxHostConfig })` (VMID-bound guest SSH) | refuses if `/opt/hermes/instances/<id>` is not this instance; records counts (sessions, messages, skills, cron jobs, profiles, env key names); stops every `agent-<id>` container; zips the Hermes home and tars the workspace; encrypts and splits; result: `{ parts: [{ name, bytes, sha256 }], counts, managedModel: bool }`. On any failure it starts the containers again. |
| `upload` | old guest, root | same | uploads each part to its signed URL; result `{ uploaded: n }`. Containers stay stopped. |
| `unpack` | new guest, root | `buildPinnedGuestHostScript` via `runProxmoxHostScript` | downloads and checks parts; stops `bux-hermes` and the Hermes gateway; keeps the fresh install's managed model wiring aside; runs `sudo -u bux hermes import <zip> --force`; extracts the workspace; rewrites `/home/hermes/.hermes` to `/home/bux/.hermes` in config and cron files; removes container-only env lines (`HERMES_INSTANCE_ID`, `HERMES_DASHBOARD_URL`, `API_SERVER_*`, `BROWSER_CDP_URL`, `HERMES_BROWSER_SIDECAR_AUTH_TOKEN`, `TERMINAL_ENV`, `TERMINAL_STRICT_BACKEND`); when the old agent used managed inference, re-applies the new computer's managed wiring (provider, base URL, key) and keeps the owner's model choice; starts the dashboard and the gateway; checks the counts match `pack`'s; result `{ counts, gateway: "running|stopped" }`. On failure it leaves the new computer stopped. |
| `restart-old` | old guest, root | same as pack | starts every `agent-<id>` container again (used by failure and undo). |

## The move record

Table `hermes_computer_moves` (service role only):

`id uuid pk, user_id text, instance_id uuid, agent_id uuid null, state text, step text, message text,
key_encrypted text, parts jsonb, counts_before jsonb, counts_after jsonb, managed_model bool,
initiated_by text ('owner'|'operator'), error text, started_at, updated_at, finished_at, undo_until`.

`state`: `queued → launching → packing → uploading → unpacking → finishing → done`, or `failed`,
`needs_attention`, `undone`. One active move per instance (partial unique index on non-terminal states).

Advancing is idempotent and happens from two places: `GET /api/instances/[id]/move` (the owner's page
polls it) and the cron `/api/cron/advance-hermes-moves` (every 2 minutes, a few moves at a time), so a
closed browser or a fleet run still finishes.

## Switching over

On `unpack` done:

- old row: `status = 'scheduled_for_deletion'`, `scheduled_deletion_at = now() + 7 days`,
  `config.movedTo = { agentId, moveId, at }`; the old VM is shut down with `shutdownProxmoxInstance`
  (the disk is kept). The existing `purge-expired` cron deletes it after 7 days, and the slot count
  already ignores that status.
- the bankr wallet row is relinked.
- the new agent's `config.movedFrom = { instanceId, name, moveId, at }`.

The new computer is launched by the same launch code as a normal Hermes launch
(`launchHivraAgentForUser(userId, body, { moveFromInstanceId })`), sized at least to the Hermes floor and
no smaller than the old agent, named like the old agent, with managed inference. `moveFromInstanceId`
lets the slot and CPU/RAM checks leave out the instance being replaced.

## Undo

Within 7 days, **Undo move** on the new agent: stop the new computer, start the old VM and its
containers (`restart-old`), set the old row back to `running` and clear its deletion date, relink the
wallet back, delete the new computer, `state = undone`. Anything done on the new computer since the
move is lost, and the button says so.

## Fleet run (production, at ship time)

`POST /api/ops/hermes-moves` (ops admin) queues moves for chosen instances or all running old Hermes
agents, with `dryRun` to list them first. The cron advances at most `HERMES_MOVE_CONCURRENCY` (default
2) at a time. Owners get the same "Moved" notice on their new agent.

## Hermes gateway on official computers

Scheduled tasks and chat channels run inside Hermes's gateway, not its dashboard. Official Hermes
computers install it with Hermes's own `hermes gateway install` as a user service for `bux`, with
linger on, which is upstream's advice for headless VMs (so `hermes update` can restart it without
root). Existing Hermes computers get it from "Update connection service".
