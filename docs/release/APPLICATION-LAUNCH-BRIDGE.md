# Application Launch bridge candidate

This candidate carries the managed Launch and Classic compatibility paths on the production source lineage. `HIVRA_MANAGED_LAUNCH_BRIDGE`, `HIVRA_MANAGED_PLACEMENT_BRIDGE` and `HIVRA_CLASSIC_HOLDER_BRIDGE` default off. Don't turn them on until the exact database contract from [the SQL prerequisite](https://github.com/ashneil12/hivra/pull/820), delivery bundles, and operator holds are verified. Neither this candidate nor its SQL prerequisite authorizes a live change. The [frozen full sync](https://github.com/ashneil12/hivra/pull/814) is separate.

| Database phase | Managed computers | Classic computers |
| --- | --- | --- |
| `legacy` | Stable RPCs use the legacy writer without stamping funding. Native and model receipts retain their request identity. | Create keeps legacy nullable funding. Legacy resize and power use the existing host path, so drain that work before the first breaking cut. |
| `funding` | Fresh launches require an explicitly paid entitlement and a verified empty admitted-reservation ledger. Existing receipts are read before fresh admission. Keep reservation writers frozen; the app's empty-ledger check is not in the same transaction as admission or resize. | New HermesOS creates stamp paid funding; the SQL refuses funded Proxmox placement if holder capacity is reserved. Workspace Cloud keeps separate funding. Holder wake is held until the full placement-and-repair contract exists. |
| `placement` | A separate placement opt-in enables paid-only, holder-aware host ranking and canonical transactional admission. A changed epoch or target stops dispatch, and the kickoff rechecks the selected host's bundle and runtime capabilities. | Create uses the exact registered host; ordinary Proxmox Start and live resize hold durable allocations before dispatch. Opt into holder wake only after verifying the trailing Classic repair migration and schema reload. Access to already-running holders doesn't depend on the wake switch. This candidate doesn't schedule the holder sweep or qualify new holder launches. |

## What to drain, preserve, and verify

1. Freeze old application traffic and all workers that can use the old call shape, including direct-to-deployment URLs, detached provisioning, queue consumers and callbacks. A database epoch lock fences the write transaction, not SSH started by another process. Before each cut and before app fallback, drain prior-epoch provisioning, resize, reallocation, power, restore and tier work, and keep host rotation and delivery bundles stable until dispatches settle.
2. Hold unported Classic paths until their exact replacement is accepted: admin restore-batch, workspace move, orphan/failed/stuck runtime restoration outside the owner receipt, unhealthy-active recovery, missing-VM recreation, paid auto-resume and Stripe payment power-on. Do not rely on an app read or a late DB write to block a host call already dispatched. Owner generic cap changes, direct reallocation, and cold/missing-VM restore also refuse in placement. Preserve their rows and archives.
3. After the writer returns a confirmed stale-epoch refusal, a native Launch receipt stays terminal with its original ID; a new user-initiated request may start only after that no-write outcome. A model receipt rechecks the same idempotency key and fingerprint for a concurrent winner before claiming refusal. Losing the reply or the policy changing after a write isn't proof of no write, and neither path automatically dispatches again. Check the same ID before doing any compensating work.
4. Treat unresolved Classic Start and resize receipts as outstanding capacity. After freezing new dispatch, find Start claims in the private `classic_start` table with the database operator and inspect resize claims by instance, owner, operation and host identity. Use verified host evidence to settle the original claim. Only positive evidence that Start was never dispatched, such as the exact host script's pre-start VM-missing refusal, permits releasing it. An unconfirmed operation is not a retry or a rollback candidate. Do not clear pending rows by hand or use a stopped observation as evidence of no dispatch.
5. Rehearse old and new requests, same-key replay, stale request refusal, acknowledgement loss, accepted and aborted DDL, and app fallback with isolated representative data. Before approving actual routing, repeat relevant flows on the authorized target with the hosted PostgREST cache, exact fallback build and bundle/channel, and verify current paid, mixed, and holder evidence without creating synthetic live eligibility. Live holder qualification and saved-guest wake remain open gates.

Before the holder cut, the prior build is only a fallback if the database is still on the reviewed legacy contract and all in-flight work has drained. After that cut, don't route to the old build, turn off the bridge to recover, or decrement the epoch. Use an accepted app at the current epoch or hold and roll forward. Restore/PITR is a separate decision; the offline transaction rollback doesn't prove recovery over real writes.
