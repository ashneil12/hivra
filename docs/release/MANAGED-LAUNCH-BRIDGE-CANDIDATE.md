# Managed Launch rolling compatibility runbook

**Keep the breaking #814 steps on hold until the bridge app is accepted.** Migration `20261126192500_managed_launch_bridge.sql` is an additive prerequisite for the two managed Launch writers. It is not a deployable bridge app or a qualified rollback. Production `408e6b6f` can serve unchanged while the prerequisite is installed and during the additive seat-funding migration. It cannot serve managed Launch after the holder migration. Replace it with a separately staged bridge app before crossing that boundary. This runbook does not authorize a live migration, promotion, or rollback.

The source scope is #814 at `72bc48dff37a856ef8eb29933d201c2f86ceb426` / tree `612d7aca9aa88635eb745527537c66931d58de7a`, with frozen Canary parent `4bfe13577cd2dd7baa8917b970b5a3a6fa133cab` (#810). Nothing from #811 or #812 is in scope. Do not edit migrations already applied on Canary.

## Why the bridge takes explicit funding

The live direct and Codex receipt writers omit `seat_funding`; the holder migration rejects both. Durable placement replaces both signatures with trailing default arguments, so the old shape still resolves in PostgreSQL but still fails validation. The missing JSON key alone cannot distinguish a legacy worker from a malformed current request, a paid seat from a holder seat, or a previously committed receipt from a new allocation.

`holder_admission_has_paid_access` is a grandfathering evidence predicate, not the runtime billing resolver. It includes Workspace Cloud, which is a separate lane from standard Launch; it also does not make the launch gate's free/trial, supported-runtime, sleep/wake, or resource decisions. Reusing it to fill an omitted key would hide an application regression and could misclassify a new seat. Leaving new rows null after the holder cutover would skip holder accounting. Reintroducing short signatures beside defaulted signatures also changes function resolution and doesn't solve funding.

## Candidate order and exact contracts

1. **Expand without changing existing writers.** Review and apply only `20261126192500` on the exact approved database in its own atomic migration/ledger transaction. In production explicitly select this version rather than running a bulk migration push, which would encounter the lower breaking versions first. The migration starts verified pre-holder production in `legacy` and already-migrated Canary in `placement`; it refuses unknown, mixed or halfway `funding` state. It checks canonical names, exact signatures/bodies/grants and relevant supporting SQL; separately verify the target ledger and any non-Launch schema drift. Don't reapply historical migrations to Canary. Verify hosted PostgREST sees the new names and grants. In `legacy` the adapters delegate without stamping a cohort; existing rules, legacy nulls, and later grandfathering stay unchanged. The old app can continue serving in this phase. The additive `20261124010000` can also be applied and verified here.
2. **Stage and qualify a bridge app from `408e6b6f`.** Change `launch-agent.ts` and `launch-model-store.ts` to issue the bridge variants, with unchanged request and operation IDs, fingerprints, model selection and slot limits. Read the epoch per request, before resolving managed entitlements and ranking hosts; use the legacy gates in `legacy`, and the matching #814 entitlement, funding, runtime/sleep, and holder placement paths in `funding` and `placement`. Resolve funding server-side from the same effective entitlement used for resource/slot limits (paid precedence in mixed accounts; holder requires a current eligible admission, runtime support, and wake-ready placement). Use the existing non-managed receipt path without synthesizing funding. Read failures must fail closed in the bridge, not fall back to the legacy epoch or a paid cohort. Pass the configured placement arguments explicitly; never swap in SQL defaults on error. If the adapter definitively returns `bridge_phase_changed` before mutation, reconcile the existing request/operation first, then allow a fresh admission with a fresh epoch and the same idempotency identity. A network/acknowledgement failure is not that refusal; keep existing uncertain-write reconciliation and never dispatch a second guest.
3. **Switch production routing to the *qualified bridge*, then drain the old writers.** Confirm all managed creation entry points, cron/jobs, detached execution, and requests started through the old deployment have stopped issuing the old shape, including rollback URLs and any traffic bypassing the main alias. Do not rely on timestamps or DNS promotion alone. If routing and draining can't be proved, don't cross the breaking seam. Protect new traffic against stale decisions using the epoch check at the write boundary.
4. **Commit `20261124230000` and the `funding` epoch together.** Follow the atomic recipe below. Adapter calls hold a shared lock on the epoch row for their write transaction; the cutover must take the exclusive lock before executing DDL. The funding adapters pass the explicit cohort to the strict reviewed writers, so holder triggers, grandfathering/backfill and request replay are unchanged. Verify bridge availability and successful writes before proceeding.
5. **Apply the intervening files in pinned order, then commit `20261125040000` and the `placement` epoch together.** Use the same recipe, then apply the trailing migration files. The adapters now delegate with both placement arguments and leave the final SQL signatures and guards intact. Confirm PostgREST resolves the unchanged adapter names and the exact explicit final contracts, and that no old short-shape calls are serving paid Launch.
6. **Promote #814 only after its own approval and acceptance.** Keep the exact qualified bridge app and adapter schema as the app fallback during observation. Before the first breaking commit, reverting app traffic to `408e6b6f` is permissible only if the database is still in `legacy` and the fleet/bundle checks permit it. After that commit, rollback means app traffic to the qualified bridge on the *current* epoch, or a newly qualified roll-forward from the #810 scope; it does not mean decrementing the epoch, restoring over live writes, or routing to `408e6b6f`. Remove the temporary bridge only in a later reviewed contraction after the fallback and all caller dependencies are retired.

### Atomic operator recipe

Verify the release pin, exact historical file digest, approved environment and predecessor ledger before composing the transaction. Use the migration owner (or its approved operator role), never `service_role`. Do not apply either historical file independently. Adapt the reviewed per-file migration wrapper so it executes the following in **one session, one transaction**, with stop-on-error; include the wrapper's actual ledger guard and write, not a second ledger repair command.

| Historical file | `p_expected` | `p_next` |
| --- | --- | --- |
| `20261124230000_holder_admissions.sql` | `legacy` | `funding` |
| `20261125040000_durable_proxmox_placement.sql` | `funding` | `placement` |

```sql
begin;
set local lock_timeout = '5s';
set local statement_timeout = '45s';
select managed_launch_bridge_private.begin_transition('legacy', 'funding');
-- Existing in-transaction ledger guard and byte-for-byte historical SQL.
select managed_launch_bridge_private.finish_transition('legacy', 'funding');
-- Existing in-transaction migration ledger write.
notify pgrst, 'reload schema';
commit;
```

The private hooks check the predecessor before the DDL and the exact successor afterwards. Finishing in another transaction is rejected. A failed or timed-out transaction leaves the previous epoch, SQL and ledger in place; verify them before starting again and never move the marker by hand. After commit, verify the new epoch and expected hosted service-role writes, transaction/receipt replay, row/grant effects, and actual migration ledger. Stop on any unexpected mismatch. Restoration/PITR is a separate incident decision, not an app fallback.

## Work required before the candidate can serve traffic

The fixture only covers the two managed Launch writers. The app fallback cannot be made operational by applying it alone: old Classic creation writes `hermes_instances` directly, whereas #814 stamps the cohort and routes Proxmox creation through `insert_hermes_instance` for capacity. A bridge must carry the phase-specific Classic creation path (legacy insert, explicit paid insert with new Classic holder launches denied, then durable Proxmox writer), fenced by the same epoch at mutation time, plus the schema-appropriate lifecycle callers for existing paid and grandfathered seats. Qualify payment/provider-triggered creation, resize, start and wake, not just HTTP Launch. Separately inventory any live prepared Omarchy caller: `reserve_hivra_prepared_omarchy` calls the short direct writer; current public copy says new claims are paused. Prove that hold applies to every release target, or update its provider-side admission and placement call with explicit evidence under separate scope. Don't treat the hold as evidence that the SQL works. Do not enable holder sleep, runtime previews or other flags as part of this compatibility work.

Run local and hosted acceptance against the exact candidate and its fallback: native concurrent transactions straddling both epoch commits (including lock timeout/aborted migration), one-create receipt replays after a cutoff or lost acknowledgement, slot and independent CPU/RAM/disk exhaustion, new admitted and waitlisted holders, paid and holder seats on a mixed account, expired/grace/zero-slot entitlements, Workspace Cloud isolation, exact service-role PostgREST calls and cache reload, and billing/Classic lifecycle including runtime bundle backward compatibility. The bridge app needs tests of epoch errors and idempotent recovery before it can become a rollback target. Restore/PITR is a separate rehearsal on isolated infrastructure; do not conflate it with app rollback.

## Native regression and limits

Run `bash scripts/release/test-managed-launch-bridge.sh` from the repository with Node, Docker and the three images pinned in the script already present. The disposable PostgreSQL and PostgREST containers share a network namespace with only loopback and no mapped port. The fixture uses synthetic data and platform stubs, not a production dump. It applies the additive migration independently to both endpoint schemas and verifies refusal for mixed state, exposed grants, an extra overload and altered search path. Native and HTTP probes compare old, bridge and final named-argument call shapes at the cutovers and after all 12 historical delta files. The raw writers insert/reserve before and after `20261124010000`, then return `invalid_request`; the adapters insert/reserve throughout. Native tests cover paid and admitted-holder persistence, legacy receipt replay at the slot limit, fingerprint conflict, waitlist rollback, stale epoch denial, capacity refusal and private grants. HTTP tests verify PostgREST resolves the service-role calls and denies anonymous execution. Two-session probes verify that each cutover waits for an in-flight writer; aborted cutovers leave the predecessor epoch and ledger intact. This does not qualify hosted PostgREST, app rollback, live traffic, or runtime availability.
