# Managed Launch rolling compatibility runbook

**Keep the breaking #814 steps on hold until the bridge app is accepted.** The additive prerequisites are `20261126192500_managed_launch_bridge.sql` for the two managed Launch writers, `20261126194500_classic_placement_bridge.sql` for Classic create and ordinary Proxmox Start, and `20261126202000_managed_writer_drain.sql` for the database writer fence. They are not a deployable bridge app or a qualified rollback. Production `408e6b6f` can serve unchanged while those prerequisites are installed and the fence is open. It cannot serve managed Launch after the holder migration. Replace it with a separately staged bridge app before crossing that boundary. This runbook does not authorize a live migration, promotion, or rollback.

The source scope is #814 at `72bc48dff37a856ef8eb29933d201c2f86ceb426` / tree `612d7aca9aa88635eb745527537c66931d58de7a`, with frozen Canary parent `4bfe13577cd2dd7baa8917b970b5a3a6fa133cab` (#810). Nothing from #811 or #812 is in scope. Do not edit migrations already applied on Canary.

## Why the bridge takes explicit funding

The live direct and Codex receipt writers omit `seat_funding`; the holder migration rejects both. Durable placement replaces both signatures with trailing default arguments, so the old shape still resolves in PostgreSQL but still fails validation. The missing JSON key alone cannot distinguish a legacy worker from a malformed current request, a paid seat from a holder seat, or a previously committed receipt from a new allocation.

`holder_admission_has_paid_access` is a grandfathering evidence predicate, not the runtime billing resolver. It includes Workspace Cloud, which is a separate lane from standard Launch; it also does not make the launch gate's free/trial, supported-runtime, sleep/wake, or resource decisions. Reusing it to fill an omitted key would hide an application regression and could misclassify a new seat. Leaving new rows null after the holder cutover would skip holder accounting. Reintroducing short signatures beside defaulted signatures also changes function resolution and doesn't solve funding.

## Candidate order and exact contracts

1. **Expand without changing existing writers.** Review and apply only `20261126192500`, `20261126194500`, then `20261126202000` on the exact approved database, each in its own atomic migration/ledger transaction. Explicitly select these versions rather than running a bulk migration push, which would encounter the lower breaking versions first. The first migration starts verified pre-holder production in `legacy` and already-migrated Canary in `placement`; it refuses unknown, mixed or halfway `funding` state. It checks canonical names, bodies and relevant grants and supporting SQL; separately verify the target ledger and any non-Launch schema drift. Don't reapply historical migrations to Canary. Verify hosted PostgREST sees the new names and grants. In `legacy` the adapters write without stamping a cohort; existing rules, legacy nulls, and later grandfathering stay unchanged. The old app can continue serving with the database fence open. The additive `20261124010000` can also be applied and verified here.
2. **Stage and qualify the main-based bridge app.** Change the managed Launch writers to issue the bridge variants with unchanged request and operation IDs, fingerprints, model selection and slot limits. Read the epoch before resolving entitlements and ranking hosts. Use the legacy gates in `legacy`; in later epochs require an explicit paid entitlement from the same policy used for resource and slot limits. The prerequisite SQL can exercise holder funding offline, but the app companion must not initiate holder-only launches without accepted runtime and wake support. Use the existing non-managed receipt path without synthesizing funding. Read failures must fail closed, not fall back to the legacy epoch or infer paid access. Pass the configured placement arguments explicitly. If the adapter definitively returns `bridge_phase_changed` before mutation, reconcile the existing request/operation first, then allow a fresh admission with a fresh epoch and the same idempotency identity. A network/acknowledgement failure is not that refusal; keep existing uncertain-write reconciliation and never dispatch a second guest.
3. **Fence ingress and drain old workers before crossing either cut.** Stop accepting work from old deployments before they can issue database or host calls. Cover direct deployment URLs and aliases, public/API traffic, cron, webhooks, queued and detached execution, and provider/SSH jobs. Close and commit the database gate as described below; a subsequent empty database inventory is necessary but not proof of worker shutdown. If old deployments share the same database role as the companion, reopening the database alone would allow them to write again. Prove their ingress and host dispatch are revoked independently, or keep the whole path closed.
4. **Commit `20261124230000` and the `funding` epoch together.** Follow the atomic recipe below. Adapter calls hold a shared lock on the epoch row for their write transaction; the cutover must take the exclusive lock before executing DDL. The funding adapters pass the explicit cohort to the strict reviewed writers, so holder triggers, grandfathering/backfill and request replay are unchanged. Verify bridge availability and successful writes before proceeding.
5. **Apply the intervening files in pinned order, then commit `20261125040000` and the `placement` epoch together.** Use the same recipe, then apply the trailing migration files. The adapters now delegate with both placement arguments and leave the final SQL signatures and guards intact. Confirm PostgREST resolves the unchanged adapter names and the exact explicit final contracts, and that no old short-shape calls are serving paid Launch.
6. **Promote #814 only after its own approval and acceptance.** Keep the exact qualified bridge app and adapter schema as the app fallback during observation. Before the first breaking commit, reverting app traffic to `408e6b6f` is permissible only if the database is still in `legacy` and the fleet/bundle checks permit it. After that commit, rollback means app traffic to the qualified bridge on the *current* epoch, or a newly qualified roll-forward from the #810 scope; it does not mean decrementing the epoch, restoring over live writes, or routing to `408e6b6f`. Remove the temporary bridge only in a later reviewed contraction after the fallback and all caller dependencies are retired.

### Atomic operator recipe

Verify the release pin, exact historical file digest, approved environment and predecessor ledger. Use a fresh `READ COMMITTED` connection directly authenticated as the private contract's migration owner, with no `SET ROLE service_role`. Verify `session_user`, effective role, and the owner rather than assuming an elevated pooled connection is equivalent.

1. Close the database writer gate in its **own committed transaction** with `set_writer_drain('<predecessor>', true)` in `managed_launch_bridge_private`, using bounded lock and statement timeouts. It waits for already-active guarded transactions to release their locks. On lock timeout, the close did not commit; prove the state and stop. Once closed, legacy direct Classic writes, managed writes and operation journal mutations refuse with `P0059`; read-only inspection stays available. This is an interruption to managed, Classic, model delivery and move writes, including otherwise valid requests.
2. Prove no old/cached host operation can start independently of the database. Inspect `writer_drain_pending()` and reconcile exact existing operations under the closed gate. An unknown Start, resize, model dispatch or save is not eligible for replay, timeout-based expiry, or release. With verified owner, target, operation and host evidence, the migration owner can use `begin_writer_reconciliation('<epoch>')` in a fresh transaction and invoke the already-reviewed settlement RPC for that same receipt. There is one narrow journal-only release: `release_expired_custody_attempt(owner, request_id, attempt_id)` clears the exact expired lease on a waiting request only if it never created a delivery operation. It preserves the original receipt, intent and attempt history. A failed reconciliation transaction leaves the original receipt and gate intact. Never clear the gate to make a stuck journal writable to the app.
3. After a clean inventory and proven external drain, apply the historical file using the reviewed per-file wrapper in **one session, one transaction**, with stop-on-error. Include the actual ledger guard and write, not a second ledger repair command.

## Work required before the candidate can serve traffic

Classic create uses the same epoch fence. It leaves funding unset in `legacy`, requires explicit paid funding for HermesOS at the later cuts, and preserves the separate unfunded Workspace Cloud lane. When holder capacity is reserved, fresh HermesOS Proxmox creates refuse in `funding` because no durable placement writer is installed yet. At `placement` Classic uses the canonical capacity authority and the exact registry ID when a host is registered. The existing empty-registry and dedicated Workspace Cloud fallback cases have no measured registry authority; they do not qualify a live fallback on their own. Old direct Classic writers still bypass placement and must be drained before it is activated.

Ordinary Classic Proxmox Start at `placement` reserves capacity and records the exact instance, owner, host, VMID and operation before dispatch. Only `claimed` permits dispatch; a timeout or ambiguous host outcome leaves the charge and receipt pending and blocks competing lifecycle, target, allocation or delete writes. This is not the holder-idle wake path. To prepare rollback or adapter removal, freeze new Starts and have the database operator inspect pending rows in `managed_launch_bridge_private.classic_start` (`outcome is null`). The database record identifies the exact guest and operation; it does not establish whether Start happened. Settle with the reviewed finish RPC only after independent host evidence confirms this guest started, or proves the Start was never dispatched. A stopped observation alone doesn't establish the latter. If neither can be established, keep the reservation and don't remove the guard, retry Start, or route around it. There is no automatic reconciler in this prerequisite.

Qualify payment/provider-triggered creation, resize, Start and holder wake against the companion app, not just the HTTP Launch writer. Before each epoch change, stop accepting and drain legacy host operations that don't hold the database epoch across their SSH work; a new epoch read at request start doesn't cover a delayed host dispatch. Separately inventory any live prepared Omarchy caller: `reserve_hivra_prepared_omarchy` calls the short direct writer; current public copy says new claims are paused. Prove that hold applies to every release target, or update its provider-side admission and placement call with explicit evidence under separate scope. Don't treat the hold as evidence that the SQL works. Do not enable holder sleep, runtime previews or other flags as part of this compatibility work.

Run local and hosted acceptance against the exact candidate and its fallback: native concurrent transactions straddling both epoch commits (including lock timeout/aborted migration), one-create receipt replays after a cutoff or lost acknowledgement, slot and independent CPU/RAM/disk exhaustion, new admitted and waitlisted holders, paid and holder seats on a mixed account, expired/grace/zero-slot entitlements, Workspace Cloud isolation, exact service-role PostgREST calls and cache reload, and billing/Classic lifecycle including runtime bundle backward compatibility. The bridge app needs tests of epoch errors and idempotent recovery before it can become a rollback target. Restore/PITR is a separate rehearsal on isolated infrastructure; do not conflate it with app rollback.

## Native regression and limits

Run `bash scripts/release/test-managed-launch-bridge.sh` from the repository with Node, Docker and the three images pinned in the script already present. The disposable PostgreSQL and PostgREST containers share a network namespace with only loopback and no mapped port. The fixture uses synthetic data and platform stubs, not a production dump. It applies the additive migration independently to both endpoint schemas and verifies refusal for mixed state, exposed grants, an extra overload and altered search path. Native and HTTP probes compare old, bridge and final named-argument call shapes at the cutovers and after all 12 historical delta files. The raw writers insert/reserve before and after `20261124010000`, then return `invalid_request`; the adapters insert/reserve throughout. Native tests cover paid and admitted-holder persistence, legacy receipt replay at the slot limit, fingerprint conflict, waitlist rollback, stale epoch denial, capacity refusal and private grants. HTTP tests verify PostgREST resolves the service-role calls and denies anonymous execution. Two-session probes verify that each cutover waits for an in-flight writer; aborted cutovers leave the predecessor epoch and ledger intact. This does not qualify hosted PostgREST, app rollback, live traffic, or runtime availability.
