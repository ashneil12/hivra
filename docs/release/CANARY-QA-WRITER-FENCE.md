# Canary QA writer fence

This is a default-off prerequisite for a bounded Canary rehearsal, not an active Canary configuration or a replacement for the database-wide release drain. The migration enrolls no owner, creates no login or grants for application roles, and opens no writer generation. No existing application route, cron, host command or bundle uses the adapter.

## Boundaries

- The database fence scopes one existing owner and one preassigned Proxmox host/VMID. It checks database-authenticated roles, not a caller header, and protects writes to the Classic and managed rows, native and model Launch journals, model delivery journal, and workspace move journal. A QA role cannot write another owner through these boundaries or create a compute row with an unbound or different target. Existing Launch paths that allocate an ID after insert require a separate scoped integration; do not open an unbound exception. Ordinary writers for unrelated owners keep their existing behavior, including while an operator holds the enrolled owner's scope lock.
- A restricted dispatcher takes its owner/target and per-generation database client from trusted configuration. It only invokes its typed host handler for a new exact claim. A replay returns the stored result without dispatching; an unconfirmed result keeps its original receipt. Closing a generation denies new claims and prevents a new generation from opening until the pending dispatch is settled. An old role cannot be reopened, even for rollback.
- This does not retroactively revoke an older deployment's SSH key, webhook permissions or control-plane access. If an old client can issue ordinary commands to the proposed QA slot outside the restricted dispatcher, the slot is not isolated. Do not grant the QA roles shared service-role inheritance, unrestricted table access, or blanket canonical writer grants. The offline fixture uses a narrow test-only grant to exercise a representative existing security-definer writer; it does not describe live grants.

## Git-only hosted rehearsal, after separate authorization

1. Pin the current Canary Git deployment, the QA-owned slot, and its exact approved bundle. Verify the deployment is Git-sourced and get an independent verdict on the baseline. Before enrolling the standing owner, prove the old app, authenticated direct deployment URLs, webhooks, cron, detached jobs and any ordinary host access can be stopped for this slot without revoking shared credentials or interrupting other owners. Verify the real PostgREST role mapping and independently restricted delivery authority. Stop if the old path can still dispatch directly.
2. Land a reviewed, owner-scoped integration by PR into `canary`, leaving non-cohort routes unchanged. Give each generation a new least-privileged `hivra_canary_qa_…` role through approved auth, with no role inheritance. Bind the database and isolated host dispatcher to that authenticated identity and the one QA slot. Rehearse normal signed-in operations with the standing account; do not enroll a second account, charge a purchase, switch on general placement, or use a customer fixture.
3. Close and commit the enrolled scope in an operator `READ COMMITTED` transaction, and independently fence the outgoing deployment's ingress and old host dispatch. With the same approved test auth, prove its direct URL and delayed worker requests no longer admit work; require denial at the relevant authority and evidence of no new receipt or host dispatch. Don't count a pre-existing login redirect as revocation. Inspect pending receipts while closed, and only settle the exact owner, host, VM, action and operation after positive outcome evidence. Unknown is not permission to retry.
4. After a second reviewed PR lands and Canary serves its exact merge SHA, open a new generation for at most one hour and verify managed native and model Launch, Classic owner Start/resize and exact receipt replay. Keep one in-flight dispatch for the slot. Roll back by a Git revert PR to code compatible with the current placement schema. Revoke the outgoing generation, check that both former identities still fail, and give the Git fallback its own unused generation. Verify the old receipt and state before reopening; if an outcome stays unknown, leave the QA lane closed and stop.

The migration and test do not down-migrate Canary or certify the earlier schema cuts, live holder qualification, or a real runtime fallback. The isolated rehearsal uses the pinned Canary migrations, PostgreSQL, PostgREST and a recording host handler on a loopback-only container network:

```sh
bash scripts/release/test-canary-qa-writer-fence.sh --pull-test-images
```
