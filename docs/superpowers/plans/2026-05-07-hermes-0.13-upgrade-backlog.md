## Recommended Work Tracks

### Track 1: Upstream 0.13 fork sync

This is the actual version-upgrade track.

**Do now**
- Audit the delta from fork `0.12.0` to upstream `0.13.0`
- Create a dedicated sync branch in the vanilla fork
- Merge upstream main into the fork with the same fork-change rubric used for the last sync
- Re-run the Hermes Deploy upstream audit against the new fork SHA

**Focus areas during conflict review**
- `web_server.py` / dashboard plugin surfaces
- provider/plugin registry changes
- gateway auth / session persistence changes
- security defaults, especially redaction behavior
- memory/session header changes like `X-Hermes-Session-Key`

**Why this matters**
- Hermes Deploy is now truly behind in version, not just behind in additive product ideas
- upstream `0.13.0` shipped security-sensitive changes, plugin growth, session resilience, and dashboard surface work

### Track 2: Copy the upstream TUI experience selectively

Do not literally transplant the upstream Ink TUI. Copy the interaction model.

**What to copy**
- model picker behavior
- session/workspace awareness
- richer status + activity visibility
- queued-input / in-flight guidance
- command discoverability
- clearer fallback messaging when a native TUI path degrades

**What not to copy blindly**
- raw renderer internals
- terminal-only assumptions that make sense in Ink but not in a browser shell

**Ship order**
1. make the current TUI path trustworthy and explain fallbacks clearly
2. add structured overlays around the existing terminal
3. improve entry points and naming so users know when they are in quick terminal vs dedicated Hermes TUI

### Track 3: Finish the unified capability system

This is the backbone that ties commands, skills, plugins, and quick actions together.

**Do now**
- move from “partially unified in chat” to “shared source of truth across chat + skills + plugin surfaces”
- promote command registry from front-end composition into an explicit server-backed capability contract

**Why**
- this is already partly implemented, which makes it high leverage
- it solves real drift: slash commands, skills, and plugins should not feel like three unrelated systems

## Product Backlog

### Highest Priority

1. **Finish the shared command/capability registry**
   Use one payload for built-ins, runtime commands, skills, dashboard plugins, categories, aliases, and enabled state.

2. **Upgrade the web TUI experience**
   Add upstream-inspired overlays on top of the current terminal rather than leaving everything hidden inside the xterm stream.

3. **Copy the upstream Plugins page idea**
   Upstream now has a real Plugins page with management, enable/disable, and auth visibility. Hermes Deploy should expose the same concept instead of keeping plugins as hidden plumbing.

4. **Improve browser setup wording and structure**
   Reframe browser choices by user intent:
   - local/simple
   - cloud/browser fleet
   - anti-detect/persistent
   - Nous gateway-backed
   - advanced CDP attach

5. **Make profiles more visible**
   Upstream’s dashboard grew profile management. Hermes Deploy already has profile APIs, but the product surface still feels more backend-first than operator-first.

### Tools Worth Adding Now

These are the tool additions most likely to improve the product soon rather than just increase surface area.

1. **`video_analyze`**
   Good fit for a hosted agent product because it is concrete, demoable, and distinct from generic chat.

2. **SearXNG search support**
   Especially attractive if the goal is reducing dependence on third-party paid search APIs and making the “search vs extract vs browse” split more explicit.

3. **`/goal` and queue-style workflow affordances**
   Not just as commands, but as web-visible operator controls. This helps the site feel more like a real agent console and less like a thin chat wrapper.

4. **Plugin-auth visibility**
   Even before every plugin is editable, users should be able to see what exists, whether it is enabled, and whether auth is satisfied.

5. **Shared OAuth across profiles**
   This is a meaningful usability upgrade if Hermes Deploy leans into multi-profile setups.

### Add Soon, But Not First

1. **xAI custom voices**
   Nice addition if voice is becoming important, but not a core blocker.

2. **Google Chat platform exposure**
   Worth it if messaging-platform expansion is on the product roadmap, otherwise defer.

3. **Curator subcommand UX**
   Strong feature, but it should come after the capability model is cleaner.

4. **Kanban / multi-agent board UI**
   Powerful, but bigger than the current “make the product feel sharp and coherent” need.

### Defer

1. Advanced Browserbase knobs
2. Advanced gateway override fields
3. Modal-backed terminal/subscription options
4. Full CDP local connector UX
5. Large provider-by-provider UI expansion

## Concrete Implementation Order

### Phase 1: Stabilize and expose what already exists

- Re-check TUI/fallback behavior and keep the visible reason plumbing
- Add an explicit capability registry API route
- Move chat to consume only that route
- Reuse the same route in the Skills area

### Phase 2: Copy upstream product patterns

- Add a proper Plugins page or plugin mode inside Skills
- Upgrade dedicated TUI and quick terminal entry points/copy
- Add richer TUI overlays for model/session/activity/approval state

### Phase 3: Tool additions that change product perception

- add `video_analyze`
- add SearXNG search mode and clearer web-tool capability separation
- add `/goal`-style operator guidance and queue affordances

### Phase 4: Fork sync completion and follow-up

- complete the fork merge to upstream `0.13.0`
- re-run audit against the new fork SHA
- test Hermes Deploy against the new synced image
- then decide whether security-default changes like redaction behavior should stay upstream-default or remain opinionated in the fork

## Decisions We Should Make Before Building

1. **Are we copying upstream TUI behavior, or just fixing the current TUI transport?**
   Recommendation: copy behavior, not renderer code.

2. **Do plugins live inside Skills or get their own top-level page?**
   Recommendation: ship inside the Skills/capability system first, then split into a dedicated page if usage justifies it.

3. **Which tools are truly “now”?**
   Recommendation: `video_analyze`, SearXNG, and `/goal`-style workflow support first.

4. **Do we want the latest upstream version first, or the product backlog first?**
   Recommendation: do them in parallel tracks, but keep the fork sync explicit and separately testable.

## Suggested First Milestone

If we want the fastest meaningful win, the first milestone should be:

1. create the shared capability registry route
2. wire chat and skills to it
3. add plugin visibility
4. tighten the dedicated TUI positioning and fallback messaging

That gives us a noticeably better product without waiting for the full upstream `0.13.0` fork merge to land.

## Plain-English Summary

We are now one real upstream version behind, so upgrading is worth doing for real, not just talking about. But the bigger opportunity is that upstream has already done a lot of the product thinking we need: better TUI behavior, clearer plugin surfaces, and more capable command/workflow UX. The best move is not to blindly “sync everything,” but to use the upgrade as a forcing function to copy the best parts that make Hermes Deploy feel sharper.

The immediate backlog should center on three things: make commands/skills/plugins feel like one system, make the site’s TUI feel much closer to upstream’s experience, and add a small number of genuinely useful tools now instead of a huge pile of settings.
